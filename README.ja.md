1. **同じ数値を与える** — 両チームの Elo レーティング、直近5試合の流れ、休養日数、xG、先発変更数を、統計モデルと LLM に**まったく同じように**入力する。
2. **同じ物差しで測る** — 勝・分・負の確率を Brier スコア・対数損失で採点し、**1つの表に並べて**置く。定数モデル（何も知らない状態）が一番下。
3. **LLM の記憶をフィルタリングする** — LLM が昨シーズンの結果を覚えている可能性があるため、**チーム名を伏せたバージョン**と比較し、「データで推論したもの」と「記憶から引き出したもの」を分離する。
4. **LLM は仮説生成器** — 「最適の11人」のような証明不可能な主張の代わりに、LLM が出した先発・戦術の仮説を過去データで**逆検証（バックテスト）**する。仮説は LLM、検証は統計。

この4つが、「AIベース」という言葉を**測定された数値**に変える仕組みです。

## 測定結果

試合結果（勝・分・負）の予測 — 学習 2022・2023シーズン → 評価 **2024シーズン 380試合**（2026-11-16, [ADR 0008](docs/adr/0008-결과-예측-통계-기준선.md)）。低いほど良い。

| モデル | Brier ↓ | 対数損失 ↓ | 正解率 |
|---|---|---|---|
| 定数（勝・分・負の割合） | 0.6595 | 1.0860 | 40.8% |
| **Elo 差のみ** | **0.6021** | **1.0048** | 53.2% |
| 特徴量モデル（Elo+流れ+休養+xG+先発変更） | 0.6071 | 1.0540 | 51.8% |
| LLM アナリスト（Gemini、同じ数値のみ入力） | 0.5938 | 0.9945 | 51.6% |
| **LLM + Elo の平均** | **0.5937** | **0.9924** | 52.4% |

同じ試合同士でペアにした Brier 差の 95% 区間（2026-11-18, [ADR 0009](docs/adr/0009-LLM-분석가-같은-숫자-같은-지표.md)）：

| 比較 | Brier 差 | 95% 区間 | 判定 |
|---|---|---|---|
| LLM − Elo | −0.0083 | −0.0226 〜 +0.0057 | 差なし（0 を含む） |
| LLM+Elo − Elo | −0.0083 | −0.0155 〜 −0.0013 | **組み合わせた方が良い** |
| チーム名を伏せた − 伏せていない（54試合） | +0.0047 | −0.0097 〜 +0.0187 | 記憶効果の根拠なし（サンプル小） |

LLM 仮説の逆検証（2026-11-18, [ADR 0010](docs/adr/0010-LLM-가설은-틀과-숫자로-받아-과거-데이터로-역검증.md)）— 97件を過去760試合で検証：根拠あり 83・サンプル不足 12・根拠なし 2。ただし、**97件すべてが Elo 差だけを使った当然の仮説**（「Elo 差が大きいとホーム勝率が高い」）であるため、「LLM が有意義な仮説を出した」とは書かない。検証の仕組みは機能しており（方向が逆の仮説2件を検出）、仮説の質はフェーズ 4.5 の課題。

プロンプトバージョン比較 — 評価ハーネス `python -m app.analysis.prompt_eval`（2026-11-19）。新しいプロンプトが良くなったかどうかはこの表の数値で語る。

| 指標 | v1（自由文の仮説、380試合） | v2（型+数値の仮説、97試合） |
|---|---|---|
| Elo 対比 Brier 差（95% 区間） | −0.0083（−0.0224 〜 +0.0063） | +0.0101（−0.0274 〜 +0.0447） |
| 検証可能な仮説 | 0% | 100% |
| 異なる仮説の数 / 使われた特徴量の種類 | — | 21個 / 1種類 |
| 非自明な仮説（Elo 単独ではないもの） | — | **0%** |
| 根拠文の数値が入力に存在する割合 | 99% | 100% |

v2 は仮説を検証できるようにしたがすべて当然の仮説だった → v3 の目標は「非自明な仮説 0%」を向上させること。v1 の 1%（4件）はすべて xG の数値だが、その後の収集が進んで値が変わったとみられ、当時の入力を保存していないため確認できない。

> xG・先発変更の特徴量は収集中（1日100回制限、約38日）であるため、特徴量モデルはまだ Elo より良くない。データが溜まり次第、同じコマンドで再度測定してこの表を更新する。測定していない数値は記載しない。

## 構造

```
                 ┌─────────────────────────── 毎日 GitHub Actions (常駐サーバーなし) ───────────────────────────┐
                 │                                                                                           │
 The Guardian ───┼─► collect.py ──► Neon PostgreSQL ◄── analysis_collect.py ──► API-Football                 │
 (原文, 24h)     │   (20クラブ)         ▲                 (ラインアップ・xG・選手スタッツ)                                  │
                 │                      │  読み込み (SQL)                                                         │
                 └──────────────────────┼─────────────────────────────────────────────────────────────────────┘
                                        │
 football-data.org ──(リクエスト時に直接)──► Next.js 16 (Vercel) ◄── ユーザー (モバイル)
                                        ▲
                     app/analysis/ ─────┘  Elo · ロジスティック · Gemini アナリスト → predictions
```

- **frontend/** Next.js 16 (Cache Components)。画面は外部 API の形を知らない：`football.ts`（呼び出し・キャッシュ）→ `mappers.ts`（純粋変換）→ `types.ts` → 画面。キーがないか失敗した場合はサンプルデータを表示するが、**「サンプルデータです」という帯を必ず**表示する。
- **backend/** Python。収集器は「ソース1つ = クラス1つ」の規約に従い、ネットワーク関数と純粋変換関数を分離して変換のみをテストする。分析モジュールは**試合前までの記録のみ**で特徴量を作成する（情報リーク禁止）。
- **DB 構造**は Alembic マイグレーションで管理し、バッチが開始するときに適用する。
- **テスト**: フロント16（Node 内蔵ランナー）、バックエンド76（pytest、インメモリ SQLite・モッククライアント）。すべてネットワークなしで動作する。

## （要約 — 全文は [docs/notes.md](docs/notes.md)）

- **規約はコードより先に読む。** 翻訳機能をすべて作り終えてから、ガーディアンの規約が翻訳・LLM 加工を禁止していることを知った。一日で撤去し、その後はソースごとに条項を ADR に引用している。
- **無料枠が設計を決める。** モデル選択（flash-lite）、まとめ呼び出し、1日90回収集バッチ、38日分の蓄積計画は、すべて制限の数値から出てきた。
- **平均だけを見て「勝った」と書かない。** LLM の Brier が Elo より低かったが、同じ試合同士でペアにしたブートストラップでは偶然と区別できなかった。結果表に判定まで載せる。
- **API の集計値を信じない。** 対戦成績の集計が間違っていて、試合リストから直接数えた。試合データの `"55%"`, `"2.43"`, `None` はすべて整える関数を通す。
- **デプロイが変わらなければ結びついたリポジトリ名から見る。** Vercel が別 GitHub アカウントの古いコピーを見ていた。Git の作成者メールアドレスも別アカウントのものだった。
- **Neon の pooler アドレスはプリペアドステートメントをサポートしていない。** 同じクエリを5回以上送ると接続が切れる → `prepare_threshold=None`。
