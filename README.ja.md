# ⚽ nexpitch

[한국어](README.md) · **日本語**

> **「スポーツデータアナリストに任せるべき分析を、AI が代わりに担えるのか？」** — プレミアリーグ全 20 クラブの試合データを使い、統計モデルと LLM にアナリストの仕事（試合前の勝・分・負の確率、その根拠、検証可能な戦術・先発に関する仮説）をさせ、その分析が本当に意味を持つのか — どれだけ当たるのか、仮説にデータ上の根拠があるのか — をアプリ自身が測定して示す、AI ベースのサッカーアプリです。

## なぜ作るのか

サッカーアプリは数多くありますが、「AI 分析」の多くはもっともらしい文章を表示するところで終わっています。nexpitch は逆のアプローチを取ります。

1. **同じ数値を与える** — 両チームの Elo レーティング、直近 5 試合の流れ、休養日数、xG、先発メンバーの変更数を、統計モデルと LLM に **まったく同じように** 入力します。
2. **同じ物差しで測る** — 勝・分・負の確率を Brier スコアと対数損失で採点し、**一つの表に並べて** 比較します。定数モデル（何も知らない状態）が最低ラインです。
3. **LLM の「記憶」を取り除く** — LLM が過去シーズンの結果を覚えている可能性があるため、**チーム名を伏せたバージョン** と比較し、「データから推論したもの」と「記憶から引き出したもの」を切り分けます。
4. **LLM は仮説生成器** — 「最適な 11 人」のような証明できない主張の代わりに、LLM が出した先発・戦術の仮説を過去データで **逆検証（バックテスト）** します。仮説は LLM、検証は統計が担当します。

この 4 つが、「AI ベース」という言葉を **測定された数値** に置き換えるための仕組みです。

## 測定結果

試合結果（勝・分・負）の予測 — 学習 2022・2023 シーズン → 評価 **2024 シーズン 380 試合**（2026-11-16, [ADR 0008](docs/adr/0008-결과-예측-통계-기준선.md)）。低いほど良い指標です。

| モデル | Brier ↓ | 対数損失 ↓ | 正解率 |
|---|---|---|---|
| 定数（勝・分・負の比率） | 0.6595 | 1.0860 | 40.8% |
| **Elo 差のみ** | **0.6021** | **1.0048** | 53.2% |
| 特徴量モデル（Elo + 流れ + 休養 + xG + 先発変更） | 0.6071 | 1.0540 | 51.8% |
| LLM アナリスト（Gemini、同じ数値のみ入力） | 0.5938 | 0.9945 | 51.6% |
| **LLM + Elo の平均** | **0.5937** | **0.9924** | 52.4% |

同じ試合同士でペアにした Brier 差の 95% 区間（2026-11-18, [ADR 0009](docs/adr/0009-LLM-분석가-같은-숫자-같은-지표.md)）：

| 比較 | Brier 差 | 95% 区間 | 判定 |
|---|---|---|---|
| LLM − Elo | −0.0083 | −0.0226 〜 +0.0057 | 差なし（0 を含む） |
| LLM+Elo − Elo | −0.0083 | −0.0155 〜 −0.0013 | **組み合わせの方が良い** |
| チーム名を伏せた版 − 伏せない版（54 試合） | +0.0047 | −0.0097 〜 +0.0187 | 記憶効果の根拠なし（標本が小さい） |

平均値だけを見ると LLM が Elo に勝っていますが、ペア・ブートストラップで確認すると偶然と区別できませんでした。そのため「LLM の方が優れている」とは書きません。確実に改善したのは LLM と Elo の組み合わせです。

LLM 仮説の逆検証（2026-11-18, [ADR 0010](docs/adr/0010-LLM-가설은-틀과-숫자로-받아-과거-데이터로-역검증.md)）— 97 件を過去 760 試合で検証：根拠あり 83・標本不足 12・根拠なし 2。ただし **97 件すべてが Elo 差だけを使った自明な仮説**（「Elo 差が大きければホーム勝率が高い」）だったため、「LLM が有意義な仮説を出した」とは書きません。検証の仕組みは機能しており（向きが逆の仮説 2 件を検出）、仮説の質はステップ 4.5 の課題です。

プロンプトのバージョン比較 — 評価ハーネス `python -m app.analysis.prompt_eval`（2026-11-19）。新しいプロンプトが改善したかどうかは、この表の数値で判断します。

| 指標 | v1（自由文の仮説、380 試合） | v2（型 + 数値の仮説、97 試合） |
|---|---|---|
| Elo との Brier 差（95% 区間） | −0.0083（−0.0224 〜 +0.0063） | +0.0101（−0.0274 〜 +0.0447） |
| 検証可能な仮説 | 0% | 100% |
| 異なる仮説の数 / 使われた特徴量の種類 | — | 21 個 / 1 種類 |
| 非自明な仮説（Elo 単独ではないもの） | — | **0%** |
| 根拠文の数値が入力に存在する割合 | 99% | 100% |

v2 で仮説は検証可能になりましたが、すべて自明な仮説でした → v3 の目標は「非自明な仮説 0%」を引き上げることです。v1 の 1%（4 件）はすべて xG の数値で、その後の収集で値が変わったためと見られますが、当時の入力を保存していないため確認できません。

> xG・先発変更の特徴量は収集中（1 日 100 回の上限、約 38 日）のため、特徴量モデルはまだ Elo を上回っていません。データが揃い次第、同じコマンドで測り直してこの表を更新します。測定していない数値は書きません。

## 構成

```
                 ┌─────────────────────────── 毎日 GitHub Actions（常駐サーバーなし） ───────────────────────────┐
                 │                                                                                                │
 The Guardian ───┼─► collect.py ──► Neon PostgreSQL ◄── analysis_collect.py ◄── API-Football                      │
 （原文, 24h）    │   （20 クラブ）       ▲                 （ラインアップ・xG・選手スタッツ）                          │
                 │                      │  読み取り（SQL）                                                          │
                 └──────────────────────┼──────────────────────────────────────────────────────────────────────────┘
                                        │
 football-data.org ──（リクエスト時に直接）──► Next.js 16 (Vercel) ◄── ユーザー（モバイル）
                                        ▲
                     app/analysis/ ─────┘  Elo · ロジスティック回帰 · Gemini アナリスト → predictions
```

- **frontend/** Next.js 16（Cache Components）。画面は外部 API の形を知りません：`football.ts`（呼び出し・キャッシュ）→ `mappers.ts`（純粋な変換）→ `types.ts` → 画面。API キーがない、または呼び出しに失敗した場合はサンプルデータを表示しますが、**「サンプルデータです」という帯を必ず** 表示します。
- **backend/** Python。収集器は「ソース 1 つ = クラス 1 つ」という規約に従い、ネットワーク関数と純粋な変換関数を分けて、変換部分だけをテストします。分析モジュールは **その試合より前の記録だけ** で特徴量を作ります（情報リーク防止）。
- **DB スキーマ** は Alembic マイグレーションで管理し、バッチの開始時に適用します。
- **テスト**：フロントエンド 16 件（Node 組み込みランナー）、バックエンド 72 件（pytest、インメモリ SQLite・フェイククライアント）。すべてネットワークなしで動きます。

## 実行方法

```bash
# フロントエンド
cd frontend
cp .env.example .env.local        # FOOTBALL_DATA_API_KEY, DATABASE_URL（なければサンプルデータで動作）
npm install && npm run dev         # http://localhost:3000
npm test                           # 変換・日付・ニュース・ラベルのテスト

# バックエンド
cd backend
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # GUARDIAN_API_KEY, DATABASE_URL, API_FOOTBALL_KEY, GEMINI_API_KEY
python -m pytest                   # 72 件、ネットワークなし
python -m alembic upgrade head     # テーブル作成・最新スキーマへ（ADR 0011）
python -m app.collect              # ニュース収集 → DB,  python -m app.cleanup  # 24 時間経過分の削除
python -m app.analysis_collect 90  # 分析データの収集（1 日の予算内で）
python -m app.analysis.run 2024    # 統計ベースラインの評価表を出力
python -m app.analysis.llm_run 2024 400 90   # LLM アナリストの実行 → 採点表（Gemini 無料枠に注意）
python -m app.analysis.prompt_eval 2024      # プロンプトのバージョン比較表（予測・仮説の質・根拠の忠実度）
python -m app.analysis.tactical_run 2024     # チームスタイル表・折半信頼性・戦術特徴量の暫定評価
```

## 学んだこと（要約 — 全文は [docs/notes.md](docs/notes.md)、韓国語）

- **規約はコードより先に読む。** 翻訳機能を作り終えた後で、ガーディアンの規約が翻訳・LLM による加工を禁止していることに気づきました。1 日で撤去し、それ以降はソースごとに条項を ADR に引用しています。
- **無料枠の上限が設計を決める。** モデルの選択（flash-lite）、まとめ呼び出し、1 日 90 回の収集バッチ、38 日がかりの蓄積計画は、すべて上限の数値から決まりました。
- **平均値だけで「勝った」と言わない。** LLM の Brier は Elo より低かったものの、同じ試合同士のペア・ブートストラップでは偶然と区別できませんでした。結果表には判定まで載せています。
- **API の集計値を鵜呑みにしない。** 対戦成績の集計が誤っていたため、試合一覧から自分で数えました。試合データの `"55%"`、`"2.43"`、`None` はすべて整形関数を通します。
- **デプロイが変わらないときは、連携しているリポジトリ名から確認する。** Vercel が別の GitHub アカウントにある古いコピーを参照していました。Git の作成者メールアドレスも別アカウントのものでした。
- **Neon の pooler アドレスはプリペアドステートメントに対応していない。** 同じクエリを 5 回以上送ると接続が切れる → `prepare_threshold=None`。
