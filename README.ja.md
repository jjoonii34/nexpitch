1. **同じ数値を与える** — 両チームの Elo レーティング、直近 5 試合の流れ、休養日数、xG、先発変更数を、統計モデルと LLM に**まったく同じように**入力する。
2. **同じ物差しで測る** — 勝・分・負の確率を Brier スコアと対数損失で採点し、**1 つの表に並べて**置く。定数モデル（何も知らない状態）が最低ライン。
3. **LLM の記憶を取り除く** — LLM が過去シーズンの結果を覚えている可能性があるため、**チーム名を伏せたバージョン**と比較し、「データから推論したもの」と「記憶から引き出したもの」を切り分ける。
4. **LLM は仮説生成器** — 「最適な 11 人」のような証明できない主張の代わりに、LLM が出した先発・戦術の仮説を過去データで**逆検証（バックテスト）**する。仮説は LLM、検証は統計。

この 4 つが、「AI ベース」という言葉を**測定された数値**に置き換えるための仕組み。

## 測定結果

試合結果（勝・分・負）の予測 — 学習 2022・2023 シーズン → 評価 **2024 シーズン 380 試合**（2026-11-16, [ADR 0008](docs/adr/0008-결과-예측-통계-기준선.md)）。低いほど良い。

| モデル | Brier ↓ | 対数損失 ↓ | 正解率 |
|---|---|---|---|
| 定数（勝・分・負の比率） | 0.6595 | 1.0860 | 40.8% |
| **Elo 差のみ** | **0.6021** | **1.0048** | 53.2% |
| 特徴量モデル（Elo+流れ+休養+xG+先発変更） | 0.6071 | 1.0540 | 51.8% |
| LLM アナリスト（Gemini、同じ数値のみ入力） | 0.5938 | 0.9945 | 51.6% |
| **LLM + Elo の平均** | **0.5937** | **0.9924** | 52.4% |

同じ試合同士でペアにした Brier 差の 95% 区間（2026-11-18, [ADR 0009](docs/adr/0009-LLM-분석가-같은-숫자-같은-지표.md)）：

| 比較 | Brier 差 | 95% 区間 | 判定 |
|---|---|---|---|
| LLM − Elo | −0.0083 | −0.0226 〜 +0.0057 | 差なし（0 を含む） |
| LLM+Elo − Elo | −0.0083 | −0.0155 〜 −0.0013 | **組み合わせの方が良い** |
| チーム名を伏せた版 − 伏せない版（54 試合） | +0.0047 | −0.0097 〜 +0.0187 | 記憶効果の根拠なし（標本が小さい） |

LLM 仮説の逆検証（2026-11-18, [ADR 0010](docs/adr/0010-LLM-가설은-틀과-숫자로-받아-과거-데이터로-역검증.md)）— 97 件を過去 760 試合で検証：根拠あり 83・標本不足 12・根拠なし 2。ただし、**97 件すべてが Elo 差だけを使った自明な仮説**（「Elo 差が大きければホーム勝率が高い」）であるため、「LLM が有意義な仮説を出した」とは書かない。検証の仕組みは機能しており（向きが逆の仮説 2 件を検出）、仮説の質はフェーズ 4.5 の課題。

プロンプトのバージョン比較 — 評価ハーネス `python -m app.analysis.prompt_eval`（2026-11-19）。新しいプロンプトが改善したかどうかは、この表の数値で示す。

| 指標 | v1（自由文の仮説、380 試合） | v2（型+数値の仮説、97 試合） |
|---|---|---|
| Elo との Brier 差（95% 区間） | −0.0083（−0.0224 〜 +0.0063） | +0.0101（−0.0274 〜 +0.0447） |
| 検証可能な仮説 | 0% | 100% |
| 異なる仮説の数 / 使われた特徴量の種類 | — | 21 個 / 1 種類 |
| 非自明な仮説（Elo 単独ではないもの） | — | **0%** |
| 根拠文の数値が入力に存在する割合 | 99% | 100% |

v2 では仮説を検証できるようにしたがすべて自明な仮説だった → v3 の目標は「非自明な仮説 0%」を向上させること。v1 の 1%（4 件）はすべて xG の数値だが、その後の収集が進んで値が変わったものとみられ、当時の入力を保存していないため確認できない。

> xG・先発変更の特徴量は収集中（1 日 100 回の上限、約 38 日）のため、特徴量モデルはまだ Elo より優れていない。データが揃い次第、同じコマンドで再度測定してこの表を更新する。測定していない数値は記載しない。

## 構成

```
                 ┌─────────────────────────── 毎日 GitHub Actions (常駐サーバーなし) ───────────────────────────┐
                 │                                                                                           │
 The Guardian ───┼─► collect.py ──► Neon PostgreSQL ◄── analysis_collect.py ──► API-Football                 │
 (原文, 24h)     │   (20 クラブ)        ▲                 (ラインアップ・xG・選手スタッツ)                                  │
                 │                      │  読み取り (SQL)                                                         │
                 └──────────────────────┼─────────────────────────────────────────────────────────────────────┘
                                        │
 football-data.org ──(リクエスト時に直接)──► Next.js 16 (Vercel) ◄── ユーザー (モバイル)
                                        ▲
                     app/analysis/ ─────┘  Elo · ロジスティック回帰 · Gemini アナリスト → predictions
```

- **frontend/** Next.js 16 (Cache Components)。画面は外部 API の構造を知らない：`football.ts`（呼び出し・キャッシュ）→ `mappers.ts`（純粋な変換）→ `types.ts` → 画面。キーがないか失敗した場合はサンプルデータを表示するが、**「サンプルデータです」という帯を必ず**表示する。
- **backend/** Python。収集器は「ソース 1 つ = クラス 1 つ」という規約に従い、ネットワーク関数と純粋な変換関数を分離して変換のみをテストする。分析モジュールは**試合前までの記録のみ**で特徴量を作成する（情報リークの禁止）。
- **DB 構造**は Alembic マイグレーションで管理し、バッチ開始時に適用する。
- **テスト**: フロントエンド 16（Node 組み込みランナー）、バックエンド 72（pytest、インメモリ SQLite・フェイククライアント）。すべてネットワークなしで実行される。

## 実行

```bash
# フロントエンド
cd frontend
cp .env.example .env.local        # FOOTBALL_DATA_API_KEY, DATABASE_URL (なければサンプルデータで動作)
npm install && npm run dev         # http://localhost:3000
npm test                           # 変換・日付・ニュース・ラベルテスト

cd backend
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # GUARDIAN_API_KEY, DATABASE_URL, API_FOOTBALL_KEY, GEMINI_API_KEY
python -m pytest                   # 72 件、ネットワークなし
python -m alembic upgrade head     # テーブル作成・最新構造に更新 (ADR 0011)
python -m app.collect              # ニュース収集 → DB,  python -m app.cleanup  # 24時間整理
python -m app.analysis_collect 90  # 分析データ収集 (1日の予算内で)

python -m app.analysis.llm_run 2024 400 90   # LLM アナリスト実行 → 採点表 (Gemini 無料制限に注意)
python -m app.analysis.prompt_eval 2024      # プロンプトバージョン比較表 (予測・仮説の質・根拠の忠実度)
python -m app.analysis.tactical_run 2024     # チームスタイル表・半数安定性・戦術特徴量の暫定評価
```

## （要約 — 全文は [docs/notes.md](docs/notes.md)）

- **規約はコードより先に読む。** 翻訳機能をすべて作成した後に、ガーディアンの規約が翻訳・LLM 加工を禁止していることを知った。一日で撤去し、それ以降はソースごとに条項を ADR に引用している。
- **無料枠の制限が設計を決める。** モデル選択（flash-lite）、まとめ呼び出し、1 日 90 回の収集バッチ、38 日分の蓄積計画は、すべて制限の数値から導かれた。
- **平均だけを見て「勝った」と書かない。** LLM の Brier が Elo より低かったが、同じ試合同士でペアにしたブートストラップでは偶然と区別できなかった。結果表に判定まで記載する。
- **API の集計値を信じない。** 対戦成績の集計が間違っており、試合リストから直接数えた。試合データの `"55%"`, `"2.43"`, `None` はすべて整形関数を通す。
- **デプロイが変わらないときは、連携されているリポジトリ名から見る。** Vercel が別 GitHub アカウントの古いコピーを見ていた。Git の作成者メールアドレスも別アカウントのものだった。
- **Neon の pooler アドレスはプリペアドステートメントをサポートしていない。** 同じクエリを 5 回以上送信すると接続が切れる → `prepare_threshold=None`。
