# ADR 0012 — README 일본어판은 GitHub Actions + Gemini로 자동 갱신

- 날짜: 2026-11-18
- 상태: 승인

## 배경
일본 기업 지원을 위해 `README.ja.md`를 손으로 만들었다. 그런데 README.md는 GitHub 웹에서 직접 고치는 경우도 있어(커밋 `a1e376e`), 손 번역만으로는 일본어판이 뒤처진다. 특히 결과 표 숫자가 두 언어에서 달라지면 "측정하지 않은 숫자는 쓰지 않는다" 원칙이 깨진다.

## 선택지
1. **Actions + Gemini 자동 번역 (채택)** — README.md가 main에 push되면 번역해 커밋. 비용 0원(호출 1~2회, 기존 `GEMINI_API_KEY`). 기계 번역이라 어색할 수 있음.
2. 손 번역만 (작업 지침 규칙) — 품질은 가장 좋지만 웹에서 직접 고친 내용은 따라가지 않는다.
3. 브라우저 번역에 맡김 — 할 일은 없지만 읽는 사람이 번역 버튼을 눌러야 한다.

번역 대상은 **내가 쓴 README**라 가디언 같은 외부 콘텐츠 약관 문제가 없다. 무료 티어 입력이 Google 제품 개선에 쓰일 수 있다는 조건은 **확인 필요**지만, README는 이미 공개 문서다.

## 결정
1번 + 손 번역과의 공존. 코드는 `backend/app/llm/readme_ja.py`, 워크플로는 `.github/workflows/readme-translate.yml`.
- **원본 지문**: README.md의 sha256(줄바꿈은 LF로 맞춤)을 README.ja.md 끝 HTML 주석에 적는다. 같으면 건너뛴다 → 같은 원본을 두 번 번역하지 않고, 사람이 고친 번역은 `python -m app.llm.readme_ja --stamp`로 지문만 맞추면 덮이지 않는다.
- **검사**: 번역 전후로 소수·백분율(결과 표), 링크 대상, 코드 블록 수가 같아야 저장한다. 실패하면 한 번 더 시도하고, 그래도 실패하면 파일을 그대로 두고 워크플로가 실패한다(Actions 탭에 빨간불).
- 언어 전환 줄과 "자동 번역" 안내문은 모델이 아니라 코드가 넣는다. 이전 번역을 용어 참고로 함께 보낸다.
- 번역 커밋은 `github-actions[bot]` 이름. GITHUB_TOKEN의 push는 워크플로를 다시 깨우지 않아 반복되지 않는다.

## 결과
- 2026-11-18 실험 2회: 1회차는 `"55%"`, `"2.43"`을 바꿔 **검사가 막았다**. 2회차는 통과했고 손 번역과 안내문 외에 차이가 없었다(이전 번역을 잘 따름). 모델이 전환 줄을 따라 써서 두 번 나오는 문제를 발견해 고쳤다. 테스트 5개(가짜 클라이언트).
- **틀릴 수 있는 것**: 검사는 숫자·링크만 본다. 문장 뜻이 틀린 번역은 못 잡는다 → 큰 변경은 손으로 번역하고 `--stamp`. Actions에서의 실제 실행은 아직 확인 전.
- **2026-11-19 수정**: Actions에서 세 번 연속 실패. 첫 번째는 하루 한도(429)를 SDK가 조용히 재시도해 10분 초과, 그 뒤는 **출력을 JSON으로 감싼 탓**이었다 — README 본문의 큰따옴표(`"55%"`)가 JSON 문자열을 끝내 버려 번역이 그 자리에서 잘렸고, 숫자 검사가 매번 같은 두 숫자(`55%`, `2.43`)가 빠졌다고 막았다. 실패한 커밋의 README로 로컬에서 재현해 확인. 번역은 구조화할 필요가 없는 긴 글이라 Markdown 그대로 받도록 바꾸고, 잘림을 잡는 제목(#) 개수 검사를 더했다. 수정 뒤 실제 호출 1회로 통과(19초).
