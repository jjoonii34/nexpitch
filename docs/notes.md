## 2026-11-14 — 경기 상세 화면

**무엇을 왜**
- 경기 카드를 누르면 `/matches/[id]`로 간다. 스코어·전반 스코어·주심, 두 팀 순위 비교, 최근 리그 5경기 흐름, 상대 전적을 보여준다.
- 무료 플랜을 직접 호출해 보니 라인업·이벤트·스탯은 오지 않는다. 그래서 API가 주는 것(스코어, 주심, 맞대결 목록)에 더해, **이미 받는 데이터로 직접 계산**한 정보를 넣었다.
  - 최근 흐름: 시즌의 끝난 경기 전체를 한 번 받아(5분 캐시) 그 팀의 직전 5경기를 골라 승·무·패를 판정한다. 팀별 API를 따로 부르지 않아 호출 수를 아낀다.
  - 상대 전적: API의 집계값이 맞지 않아(실제 5경기인데 0승 1무 0패로 옴) 경기 목록에서 직접 센다. 홈·원정이 뒤바뀐 과거 경기도 '팀' 기준으로 세고, 지금 보는 경기는 뺀다.
- 계산은 `lib/insights.ts`의 순수 함수 3개(`resultFor`, `recentForm`, `headToHead`)이고 테스트가 있다 (전체 9개 통과).
- 하단 탭은 주소를 읽어 활성 표시를 하는데, `/matches/[id]`처럼 주소가 요청마다 달라지는 화면에서는 Suspense로 감싸야 빌드가 된다.

**틀릴 수 있는 것**
- 최근 5경기는 리그 경기만이다 (컵 대회 제외). 화면에 "최근 리그 5경기"라고 적었다.
- 상세 화면 하나를 처음 열 때 API를 최대 4번 부른다. 여러 경기를 빠르게 열면 분당 10회 한도에 걸릴 수 있다 → 걸리면 "응답 오류 (429)" 띠가 뜬다.
- 진행 중·예정 경기의 상세 화면은 실제 데이터로 아직 못 봤다.

**비용**: 0원.

## 2026-11-14 — API-Football 무료 플랜 확인 (라인업 가능성)

직접 호출해 확인한 사실 (요청 6회 사용, 하루 한도 100회):
- 시즌 지정 조회(`season=2026`)는 거부된다. 무료 플랜은 2022~2024 시즌만.
- 날짜 조회는 **어제~내일 3일 창**만 허용된다. 그 밖의 날짜는 거부.
- 날짜 조회에 리그 필터를 걸려면 시즌이 필요해서, 하루치 전 세계 경기(약 1,000건)를 통째로 받아 걸러야 한다.
- 3일 창 안의 경기는 경기 id로 라인업(포메이션·선발 11명·등번호·위치)과 이벤트(골·카드·교체, 분 단위)가 온다.
- 확인 못 한 것: 프리미어리그 경기의 스탯 제공 여부(확인한 친선전은 값이 비어 있었음), 3일 창이 지난 경기를 id로 다시 조회할 수 있는지.

결론: 라인업은 "경기 전후 3일 안에 받아서 저장"해야만 쌓을 수 있다 → 저장소(DB)와 배치가 필요하다. 프론트 단독으로는 지난 경기 라인업을 보여줄 수 없다.

## 2026-11-14 — 뉴스 저장: 테이블 정의와 저장 함수

**무엇을 왜**
- 저장소는 Neon(무료 호스팅 PostgreSQL)으로 정했다 (ADR 0003). 배치(GitHub Actions)와 Vercel이 둘 다 접속할 수 있어야 해서다.
- 테이블 3개(`backend/app/models/news.py`): `clubs`(구단·가디언 태그), `articles`(기사), `article_clubs`(연결표). 한 기사가 여러 구단에 걸릴 수 있어 연결표를 따로 뒀다.
- `save_articles`(`backend/app/storage.py`): 한 구단 태그로 수집한 기사를 저장하고 그 구단과 연결한다. 먼저 `url`로 이미 있는 기사를 찾고, 없는 것만 새로 넣는다 → 같은 기사가 두 구단 태그로 들어오면 기사 1건·연결 2건.
- `backend/app/db.py`: `.env`의 `DATABASE_URL`로 접속한다. Neon이 주는 주소는 `postgresql://`로 시작하는데 우리가 쓰는 드라이버(psycopg)는 `postgresql+psycopg://`여야 해서 코드가 바꿔 준다. 주소에 비밀번호가 있으므로 출력하지 않는다.
- 라이브러리: SQLAlchemy(테이블을 Python 클래스로 정의), psycopg(PostgreSQL 접속).
- 테스트 6개는 메모리 안의 SQLite로 돈다 (전체 10개 통과). 가입·네트워크 없이 저장·중복 제거 로직을 확인한다.

**틀릴 수 있는 것**
- 실제 Neon에는 아직 접속하지 못했다 (`DATABASE_URL` 없음). SQLite에서 통과해도 PostgreSQL에서 다르게 동작할 수 있다 → 접속 후 `python -m app.db`로 확인.
- 테이블 변경 관리 도구가 없다. 지금은 테이블이 비어 있어 지우고 다시 만들면 되지만, 데이터가 쌓인 뒤 컬럼을 바꾸려면 Alembic이 필요하다.
- `url`·`title` 길이를 500자로 잡았다. 더 긴 값이 오면 PostgreSQL은 오류를 낸다 (SQLite는 통과시킴).

**비용**: 0원.

**다음 할 일**: Neon 가입 → `backend/.env`에 `DATABASE_URL` 입력 → `python -m app.db`로 테이블 생성 확인 → 구단 20개 등록 + 수집 결과 저장.

## 2026-11-14 — Neon 실제 접속 검증

- `backend/.env`에 `DATABASE_URL`을 넣고 `python -m app.db`를 실행해 Neon(PostgreSQL 18)에 테이블 3개(`article_clubs`, `articles`, `clubs`)가 만들어진 것을 확인했다. 코드 수정은 필요 없었다.
- 실제 PostgreSQL에서 저장 함수를 한 번 돌려 봤다: 같은 기사를 한 묶음에 두 번 넣어도 1건, 다른 구단으로 또 넣으면 기사 0건·연결 1건 추가. 시각은 시간대(UTC)가 붙은 채로 돌아온다. 확인 뒤 되돌려서(rollback) DB는 비어 있다.
- 접속 주소(비밀번호 포함)를 채팅에 붙여 넣었다 → Neon에서 비밀번호를 재설정하고 `.env`를 새 주소로 바꾸기로 했다. 주소는 git에 올라간 적 없다.

## 2026-11-16 — 약관 위반 발견과 준수 모드 전환 (ADR 0006)

**무엇을 왜**
- BBC RSS를 붙이려고 약관을 읽다가 가디언 Open Platform 약관을 확인했고, **이미 만든 번역 기능이 약관에 어긋났다**: 번역·수정 금지, OP Content를 AI/ML로 가공 금지, 24시간 넘게 보관 금지, 로고·바이라인·저작권 표기 필수. 번역을 만들 때 약관을 읽지 않은 것이 원인이다 (CLAUDE.md 7번에 규칙 추가).
- 즉시 준수 모드로 바꿨다: 배치에서 번역 단계 제거 → `python -m app.cleanup`(24시간 넘게 가디언 응답에 안 보인 기사 삭제)으로 교체. 수집 때 다시 본 기사는 `collected_at`을 갱신해 보관을 연장한다 ("다시 받거나 지운다"의 구현). 기존 번역 298건 전부 삭제. 화면은 원문 그대로 + "Powered by The Guardian" 로고 + 저작권 표기, 검색은 영어만.
- BBC는 취소. 15조: 피드를 바꾸지 않고 그대로 붙이는 것만 허용.
- 번역 코드·테이블은 남겨 두었다 (허용 소스가 생기면 재사용). 테스트: 백엔드 29개(정리 3개 추가), 프론트 15개 통과. lint·빌드 통과.
- 확정된 것: 가디언 무료 키 한도 초당 1·하루 500회.

**틀릴 수 있는 것**
- 약관 해석은 내 읽기다. 특히 "AI technologies ... to generate any data or content"가 단순 단어 검색·구단 연결 같은 비-LLM 처리까지 막는지는 불분명하다 → 지금은 LLM·NLP를 가디언 기사에 전혀 쓰지 않는 쪽으로 보수적으로 본다.
- 24시간 규칙을 "다시 본 기사는 연장"으로 구현했는데, 가디언이 요구하는 "re-requesting"에 해당한다고 본다. 더 엄격히 하려면 매 배치에서 전부 지우고 다시 넣으면 된다.
- football-data.org 약관은 아직 못 찾았다 (경기 데이터를 LLM 입력으로 쓰는 방향의 전제).
